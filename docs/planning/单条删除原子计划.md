## 一、交付结果

用户可以在任意文本历史卡片上点击明确的删除按钮，并获得以下可观察行为：

- 数据库事务成功后，记录才从界面移除。
- 删除失败或请求无法进入后台时，记录保持不变并显示固定重试提示。
- 删除成功后重启程序，记录不会恢复。
- 同一稳定身份重复删除返回幂等成功，不产生错误或删除其他记录。
- 删除会立即作用于当前深分页快照，并使旧搜索、首页和续页结果失效。
- 收藏和删除共用 UI 全局 mutation 互斥，同一时刻只允许一个历史变更在途。

## 二、验收场景

| 场景 | 可观察结果 |
|---|---|
| `SC-DEL-01` 正常删除 | 点击删除后先显示处理中，事务成功后卡片消失。 |
| `SC-DEL-02` 重启持久化 | 退出并重启应用后，已删除记录不会恢复。 |
| `SC-DEL-03` 失败不乐观变化 | 存储失败或队列拒绝时卡片仍在，并显示“删除失败，请重试”。 |
| `SC-DEL-04` 幂等与身份 | 记录已不存在时重复删除成功；ID 存在但哈希不符时拒绝且不删其他记录。 |
| `SC-DEL-05` 查询竞态 | 删除成功后，删除前已在途的首页或续页不能让卡片重新出现。 |
| `SC-DEL-06` 退出排空 | 点击删除后立即退出，已接受事务仍提交完成。 |
| `SC-DEL-07` 类型边界 | 当前只允许删除 text 行；非 text 行不会被存储 API 删除。 |

## 三、明确排除

- 不实现清空未收藏、清空全部或批量删除。
- 不实现确认弹窗、撤销删除、回收站或键盘删除快捷键。
- 不删除图片元数据或图片文件；图片记录要等图片生命周期契约完成后再开放删除。
- 不改变收藏、复制、搜索、分页和长文本裁剪的既有产品行为。

## 四、现状与架构证据

- `clipboard_items.id` 使用 `INTEGER PRIMARY KEY AUTOINCREMENT`，已删除 ID 不会被后续插入复用。
- `StorageClient` 的所有克隆最终进入唯一 storage worker，SQLite 操作被串行执行。
- 收藏已有容量一、关闭排空的异步桥；删除采用独立同构桥，但 UI 必须维持跨桥全局互斥。
- `UiClipboardItem` 只由文本捕获、文本启动恢复和 `HistorySummary` 的 text 类型转换产生；
  现有查询转换会拒绝非 text 摘要，因此当前卡片均为 text。
- `UiState` 已能通过 `begin_history_dataset` 推进代次并拒绝旧查询结果。
- `MemoryHistory` 需要新增按 ID 和哈希删除摘要的最小接口；当前可见快照仍须独立删除，
  不能依赖缓存集合与筛选集合恰好相同。

## 五、跨原子不变量

### 存储与幂等

1. 删除输入只含 `id + [u8; 32] content_hash`，不携带正文、预览或来源。
2. 事务内先按 ID 查询 `item_type + content_hash`：
   - 不存在：提交幂等成功，`was_deleted = false`。
   - 存在但不是 `text`：返回不可删除错误，不修改数据库。
   - 存在但哈希不符：返回身份错配，不修改数据库。
   - 类型和哈希匹配：按 ID/哈希/type 删除，影响行数必须为一。
3. SQL、触发器或影响行数异常时事务回滚，记录仍存在。
4. 不存在记录可以接受任意固定长度哈希并返回幂等成功，因为 AUTOINCREMENT 保证 ID 不复用。

### 并发与生命周期

1. Slint 回调不访问 SQLite，只同步冻结当前索引对应的 ID、哈希和面板代次。
2. UI 从请求建立到匹配结果消费期间保持全局 mutation 锁；pin/delete 任一 pending
   都拒绝新的收藏或删除请求。
3. 删除 request/result 回显 `mutation_token + panel_generation + id + hash`。
4. 结果只需与 pending 完整匹配，不要求等于当前面板代次；隐藏和重开不能吞掉已提交成功。
5. 删除桥关闭后拒绝新请求，但排空已接受请求；UI 结果投递失败不能阻塞 worker 退出。
6. 正常退出和启动失败都必须先关闭并 join capture、query、pin、delete 等所有 storage
   生产者，再调用 `storage.begin_closing()`。

### UI 与查询一致性

1. 删除点击只显示独立 pending，不在事务成功前移除卡片。
2. 成功后按 ID/哈希同时从当前最多 2,000 条快照和 MemoryHistory 移除。
3. 成功后先推进 history dataset generation，再按当前关键词和筛选查询 SQLite。
4. 入队失败或存储失败清除 pending、保留记录并显示固定文案。
5. 删除按钮只服务当前 text 卡片；存储层仍保留非 text 强制门禁，防止未来图片孤儿文件。

### 验证与仓库

1. 采用连续执行模式，同一时间只实现一个原子。
2. 每个原子只运行相关存储、桥接、UI 和按钮命中区测试，不运行全量测试。
3. 每个原子通过 DDD 后独立提交并推送已授权的 `origin/main`。
4. 三个原子全部完成后启动 Debug 程序并暂停，等待用户实际验证。

## DEL-01 文本历史幂等删除事务

- 状态：`in_progress`
- 支持的验收场景：`SC-DEL-02`、`SC-DEL-04`、`SC-DEL-07`
- 唯一目标：存储层按稳定身份幂等删除一条 text 历史。
- 当前行为与目标行为：当前 storage 只有 upsert、查询和收藏写入；完成后提供明确的
  `DeleteHistoryInput/Result`，不存在视为幂等成功，错配或非文本拒绝。
- 前置条件与依赖：ATOM-26 已完成；schema v1 的 AUTOINCREMENT 约束已经迁移校验。
- 代码定位依据：`src/storage/worker.rs` 的 `StorageCommand`、`StorageExecutor`、
  `StorageClient` 和 `set_history_pinned` 事务范式；`src/storage/mod.rs` 错误边界。
- 允许修改：`src/storage/mod.rs`、`src/storage/worker.rs` 和直接存储测试。
- 明确不修改：异步桥、UI、Slint、图片文件和 schema。
- 实现步骤：
  1. 增加拥有型删除输入、有限结果和非文本不可删除错误。
  2. 为 executor/client/command loop 增加删除接缝。
  3. 在同一事务查询身份与类型，按四分支契约返回或执行删除。
  4. 影响行数不是一时返回错误，让事务自动回滚。
- 接口、数据与错误契约：结果只含 ID、哈希和 `was_deleted`；不存在是 `Ok(false)`；
  身份错误沿用 `HistoryIdentityMismatch`；非文本使用固定错误类型。
- 边界与异常：触发器 `RAISE(ABORT)`、`RAISE(IGNORE)`、错误 ID/哈希和重复请求均须测试。
- 测试要求：首次删除和重启；重复删除；错误哈希；非 text；SQL 失败回滚；
  DELETE 影响零行回滚；worker 失败后仍可用。
- 验证命令：`cargo test --locked --lib storage::worker::tests::delete_history -- --nocapture`；
  Windows MSVC check；`git diff --check`。
- 预期结果：只有匹配 text 行被删除，所有失败保持数据库原值。
- 完成判定：定向测试、构建、差异检查和 L3 DDD 为 PASS。
- 交付给下一原子的输出：可由后台 worker 调用的幂等删除公共 API。
- 停止或重新规划条件：发现 ID 可复用或现有 schema 允许删除级联到未知数据。
- 风险等级：L3
- DDD 门禁：提交前强制审查破坏性事务、幂等和回滚语义。
- 计划提交信息：`feat(storage): [DEL-01] 增加文本历史幂等删除`

## DEL-02 有界异步删除命令桥

- 唯一目标：已接受的删除请求在后台顺序执行，并在退出前可靠排空。
- 当前行为与目标行为：收藏有独立单槽桥；完成后删除拥有同样的非阻塞、关闭排空和
  有限结果语义，且所有 worker 在 storage 关闭前被回收。
- 前置条件与依赖：DEL-01 完成。
- 代码定位依据：`src/history_mutation.rs` 的收藏桥；`src/main.rs` 的启动失败反向清理
  和正常关闭顺序；`src/app/ui_event.rs` 的 thread-local sender 绑定。
- 允许修改：`src/history_mutation.rs`、`src/command.rs`、`src/app`、`src/main.rs`
  和桥接定向测试。
- 明确不修改：删除按钮、快照移除、筛选行为和 Slint 视觉。
- 实现步骤：
  1. 增加独立容量一删除通道、request/result、有限 failure 和 submit error。
  2. worker 调用 DEL-01 API并把不存在幂等成功映射为成功结果。
  3. UI 事件入口暂时接收完成事件但不改变快照；DEL-03 再消费。
  4. main 绑定发送端，完整处理启动失败与正常退出的 close/join 顺序。

- 测试要求：满/关闭拒绝；已接受后立即 close 并重启验证删除；陈旧身份与非文本映射；
  emit false；启动和关闭顺序通过 Windows 编译接线。

  Windows MSVC check；`git diff --check`。
- 预期结果：删除 bridge 不阻塞 UI、不丢已接受事务、不泄露正文。
- 完成判定：定向测试、Windows 构建、差异检查和 L3 DDD 为 PASS。
- 交付给下一原子的输出：UI 可提交和接收的稳定删除 mutation。
- 停止或重新规划条件：独立 pin/delete bridge 无法通过 UI 全局互斥证明无竞态。

- DDD 门禁：提交前强制审查多 worker、关闭排空和有限错误映射。
- 计划提交信息：`feat(history): [DEL-02] 接入异步删除命令桥`

## DEL-03 删除按钮与查询一致性闭环

- 状态：`pending`
- 支持的验收场景：`SC-DEL-01`、`SC-DEL-03`、`SC-DEL-05`
- 唯一目标：用户点击卡片删除按钮后，只在事务成功时移除记录且不会被旧查询复活。
- 当前行为与目标行为：卡片只有收藏和复制按钮；完成后增加独立删除按钮、处理中状态
  和固定错误提示，并与收藏共享全局 mutation 互斥。
- 前置条件与依赖：DEL-02 完成。
- 代码定位依据：`ui/app-window.slint` 卡片操作区；`src/app/ui_event.rs` 的收藏 reducer、
  sender 提交和 dataset generation；`src/history.rs` 缓存协调器。
- 允许修改：上述 UI、状态、缓存模块和删除按钮/状态定向测试。
- 明确不修改：清空、确认弹窗、键盘删除、图片、复制和收藏业务语义。
- 实现步骤：
  1. 卡片增加删除回调、`delete_pending` 和独立命中区；当前 DTO 的 text-only 转换边界
     与存储 type 门禁共同保证非文本不可删除。
  2. 点击同步解析 ID/哈希，分配删除 token；pin/delete 任一 pending 时拒绝新 mutation。
  3. 请求入队失败清 pending并显示固定错误，快照不变。
  4. 完整匹配结果；成功按稳定身份移除快照和缓存，失败保留。
  5. 成功先推进 dataset，再提交当前筛选首页；隐藏/重开不取消在途删除。
- 接口、数据与错误契约：UI 固定提示“删除失败，请重试”；不展示 SQL、哈希或正文；
  当前转换测试必须继续证明非 text 摘要不能形成卡片。
- 边界与异常：删除第 1/中/末条、深分页第 100 条之后、收藏筛选、隐藏重开、
  队列拒绝、失败结果、旧 token/身份/查询均须稳定。
- 测试要求：不乐观移除；pin/delete 双向互斥；入队失败；迟到结果；隐藏完成；
  深分页删除；旧查询不复活；按钮命中区不触发收藏/复制/选择；长文本裁剪保持。
- 验证命令：收藏/删除 reducer 窄测试；删除按钮集成测试；收藏、复制、选择和长文本
  命中区回归；Windows MSVC build；`git diff --check`。
- 预期结果：删除操作符合事务后可见和数据库最终状态原则。
- 完成判定：所有窄测试、Windows 构建、差异检查和 L3 DDD 为 PASS；程序可启动。
- 交付给下一原子的输出：ATOM-27 完整用户可验证功能；ATOM-28 仍未启动。
