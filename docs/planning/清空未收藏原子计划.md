## 一、交付结果

用户可以通过明确的“清理未收藏”入口打开确认区；取消不会产生变化，确认后仅删除
SQLite 中所有未收藏文本记录。收藏文本、未来的图片/文件记录以及清空事务之后新复制的
文本均被保留。界面只在事务成功后更新，失败时保持原记录并显示固定提示。

## 二、验收场景

| 场景 | 可观察结果 |
|---|---|
| `SC-CLR-01` 取消 | 打开确认区后点击取消，不提交后台请求，界面和数据库均不变化。 |
| `SC-CLR-02` 确认 | 确认后先显示处理中；事务成功后未收藏文本消失，收藏文本保留。 |
| `SC-CLR-03` 失败 | 队列拒绝、SQL 或提交失败时记录不变，显示“清空失败，请重试”。 |
| `SC-CLR-04` 幂等 | 无未收藏文本时再次确认仍成功，不降低并发修订水位。 |
| `SC-CLR-05` 并发捕获 | 清空事务前提交的未收藏捕获被清除；事务后提交的新捕获被保留。 |
| `SC-CLR-06` 迟到事件 | 旧捕获、旧首页和旧续页不能在清空成功后复活已删除记录。 |
| `SC-CLR-07` 类型边界 | 非文本行不被删除；全部/收藏筛选、分页和启动恢复仍只查询 text。 |
| `SC-CLR-08` 退出排空 | 已接受的清空事务在退出前完成，所有存储生产者先于 storage 关闭。 |

## 三、明确排除

- 不实现清空收藏记录或清空全部；该能力属于 ATOM-29 的强确认路径。
- 不删除图片、文件元数据或磁盘资产。
- 不实现撤销、回收站、自动清理策略或键盘清空快捷键。
- 不改变复制、收藏、单条删除、搜索和分页的既有用户行为。
- 不运行全量测试；每个原子只运行本次改动相关的定向测试。

## 四、跨原子不变量

### 存储事务与操作顺序

1. 唯一 storage worker 是捕获 upsert 与清空事务的线性化点。
2. storage worker 持有进程内单调 `storage_mutation_revision`。每个文本 upsert
   和清空请求都在 SQL 前用 `checked_add` 预留下一值；耗尽时返回有限错误且不执行 SQL。
3. 仅当事务提交成功后才安装预留修订号；SQL 或提交失败不得推进修订号。
4. 文本捕获成功结果携带 `capture_revision`，清空成功结果携带 `clear_revision`。
5. 清空使用单个事务执行
   `DELETE FROM clipboard_items WHERE item_type = 'text' AND is_pinned = 0`。
6. 删除零条是幂等成功，也获得新的清空修订号；收藏文本和所有非 text 行不修改。

### UI 一致性

1. UI 维护进程生命周期内只增不减的 `active_clear_revision`，成功结果执行
   `max(active_clear_revision, clear_revision)`；隐藏、重开、取消、失败和幂等清空均不重置。
2. 每个内存摘要保留可选的运行时捕获修订号；启动恢复和查询结果没有运行时修订号，
   视为当前清空之前已经存在。
3. 清空成功只移除未收藏且运行时修订号缺失或小于 `clear_revision` 的文本；已经先到达
   UI 且修订号大于 `clear_revision` 的清空后捕获必须保留。
4. `ClipboardCaptured` 若是未收藏 text 且 `capture_revision < active_clear_revision`，
   必须拒绝；修订号更大的捕获即使复用旧数据库 ID 也必须接受。
5. 清空成功推进查询数据集代次并按当前筛选重新查询；清空前在途首页、续页或搜索结果
   不能复活记录。刷新失败仍保留已知正确的清空结果和清空后的捕获。
6. 收藏、单条删除和清空共享 UI 全局 mutation 互斥；任一 mutation 在途时拒绝另两个。

### 文本查询边界

1. 当前 UI 是文本历史面板，因此“全部”“文本”“收藏”和启动恢复均须在 SQL 输入边界
   显式设置 `item_type = 'text'`，不得依赖转换层遇到非文本后让整页失败。
2. 混合数据库中的 image/file 行必须保留，并且不得阻止文本筛选、深分页或重启恢复。

## CLR-01 存储修订号与清空事务

- 状态：`in_progress`
- 支持场景：`SC-CLR-02`、`SC-CLR-03`、`SC-CLR-04`、`SC-CLR-05`、`SC-CLR-07`
- 唯一目标：在唯一存储线程中建立可证明顺序的操作修订号，并以单个事务清除未收藏文本。
- 依赖：ATOM-27 已完成；v1 schema 和唯一 storage worker 已存在。
- 允许修改：`src/storage/mod.rs`、`src/storage/worker.rs` 及其直接定向测试。
- 明确不修改：异步清空桥、UI、Slint、图片文件和 schema。
- 实现步骤：
  1. 增加修订号耗尽有限错误、清空结果和 command/client/executor 接缝。
  2. 将文本 upsert 纳入修订号提交协议，SQL 前预留修订号，提交后再安装并返回。
  3. 增加单事务未收藏 text 删除，删除零条仍提交并返回新修订号。
  4. 证明触发器失败回滚、修订号不推进且 worker 后续仍可用。
- 数据契约：`TextUpsertResult` 增加 `mutation_revision`；`ClearUnpinnedTextResult`
  只含 `deleted_count + mutation_revision`，不含正文、哈希或来源。
- 边界测试：收藏/未收藏 text 与 image 混合；重复清空；ABORT 回滚；接近
  `u64::MAX` 的注入拒绝；失败后后续操作获得连续修订号。
- 定向验证：storage upsert revision 与 clear_unpinned 测试、Windows MSVC check、
  `git diff --check`。
- 风险等级：L3；提交前质疑事务原子性、修订号安装时机和非文本边界。
- 计划提交：`feat(storage): [CLR-01] 增加清空未收藏事务与修订号`
